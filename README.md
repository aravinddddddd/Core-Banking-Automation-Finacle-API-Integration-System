# Finacle-Style Core Banking Automation & API Integration

A Python simulation of a core-banking data-onboarding and API-validation
workflow, built and run in Google Colab.

> **Scope, stated up front:** this project models the *shape* of a core banking
> integration — bulk record onboarding, a validation endpoint, and a
> deploy/rollback cycle. It does not connect to Finacle or any real banking
> system, and every record is synthetic data generated by the notebook itself.
> The naming follows Finacle's workflow vocabulary; the implementation is a
> Flask stand-in.

---

## What it does

1. **Generates a synthetic customer dataset** — 50,000 rows
   (`customer_id`, `name`, `account_type`, `balance`, `status`) written to
   `data/customers.csv`. Balances are randomised; names are sequential
   placeholders.

2. **Loads records into SQLite** — reads the CSV with pandas, checks that every
   required field is present, and writes the complete rows to a `customers`
   table in `db/bank.db`. The loader reports its own completeness rate rather
   than assuming one. Because the generator emits all five fields for every
   row, that rate is **100%** on the bundled dataset; the check exists to catch
   incomplete rows in data that did not come from the generator.

3. **Serves a mock validation endpoint** — a Flask app exposing
   `POST /api/validateTransaction`, tunnelled out of Colab with pyngrok. The
   handler simulates a 98% success rate with a random draw, so responses
   exercise both the success and failure branches of a client.

4. **Simulates deploy and rollback** — writes and removes a deployment log
   entry, standing in for an audit-logged release cycle.

---

## Tech stack

Python 3, pandas, SQLite, Flask, pyngrok, requests. Runs in Google Colab; no
local setup required.

---

## Running it

Open the notebook in Colab (badge at the top of the file) and run the cells in
order.

The ngrok cell needs an auth token. **Do not paste it into a cell** — add it via
Colab's Secrets panel (the key icon in the left sidebar) as `NGROK_AUTHTOKEN`
and enable notebook access. The cell reads it from the environment and raises a
clear error if it is missing.

`db/bank.db` is generated by the loader cell and is not committed.

## Honest limitations

- **No Finacle integration.** No BizLogic scripts, no menu customisation, no
  Finacle Connect or FI APIs. The endpoint name is the only Finacle-shaped part.
- **Synthetic data.** Names are `Cust1`…`Cust50000`; balances are
  `random.uniform(0, 200000)`. Nothing here reflects real transaction patterns.
- **The API validates nothing.** `validateTransaction` returns success on a
  random draw; it does not check balances, account status, or transaction
  limits against the database.
- **Deploy and rollback write a single log line.** There is no artefact
  versioning, no health check, and no real rollback target.
- **No test suite.** Correctness is checked by reading printed output.
- **The notebook has duplicate loader cells** from iterating in Colab.

## What I would build next

In rough order of value:

1. Make the API actually query SQLite — reject withdrawals above the balance and
   transactions against dormant accounts, which is what the endpoint claims to do.
2. Add `pytest` coverage for the loader and the endpoint, including
   malformed-row and insufficient-balance cases.
3. Move the notebook into `scripts/` modules with a `requirements.txt` so it
   runs outside Colab.
4. Introduce deliberately dirty rows (missing fields, bad types, duplicate ids)
   so the completeness check has something real to catch and the reported rate
   becomes a measurement rather than a constant.
